# 增量PRD: Tab交互重构 + 后台管理系统

> 📎 **历史设计（v5.1）** — 本文描述的是**该版本当时的需求设计**；**现状以 [`MASTER-PLAN-2026Q4.md`](../00-strategy/MASTER-PLAN-2026Q4.md) 与 [`DATA-DICTIONARY.md`](../30-data/DATA-DICTIONARY.md) 为准**。正文保留作演进记录。

> **版本**: v5.1-incremental | **日期**: 2025-07-11 | **作者**: 产品经理 Alice
> **前置版本**: v5.0 腾讯自选股MCP数据源集成（6-Tab + 14个API）
> **原始需求**: "K线图下方6个Tab点击后没有收起机制，K线图被挤压；14个API上线后没有任何调用统计"

---

## 产品目标

解决 v5.0 遗留的两个体验与运维问题：**Tab 浮层化让 K线图保持完整可视面积**，同时**新增 /admin 后台实现 14 个 API 端点的调用追踪与可视化监控**。

## 需求池

### P0（必须完成）

#### P0-1: Tab 浮层交互重构

| 属性 | 说明 |
|------|------|
| **需求描述** | 将 K线图下方的 6 个 Tab（策略评分/资金流向/个股简况/研报/北向资金/资讯）从"展开式"改为"浮层覆盖式"。点击非策略评分 Tab 时，以半透明浮层覆盖在 K线图上方区域展示数据内容；点击浮层关闭按钮、点击浮层外部、或再次点击同一 Tab 均可收起浮层回到 K线视图。点击"策略评分"Tab 始终关闭浮层回到纯 K线视图。 |
| **涉及Tab** | 策略评分（默认视图）、资金流向、个股简况、研报、北向资金、资讯 |
| **交互规则** | 1) 点击非策略评分 Tab → 弹出该 Tab 浮层覆盖 K线图区域<br>2) 再次点击同一 Tab → 收起浮层，回到 K线视图<br>3) 点击"策略评分"Tab → 收起浮层（若存在），回到 K线视图<br>4) 点击浮层右上角关闭按钮 → 收起浮层<br>5) 点击浮层外部区域 → 收起浮层<br>6) 切换股票（code 变化）→ 自动收起浮层 |
| **浮层样式** | 暗色玻璃态（backdrop-filter: blur + rgba 半透明背景），半透明覆盖在 K线图上方，z-index 高于 K线图但低于模态弹窗。浮层标题栏含 Tab 名称 + 关闭按钮(×)。浮层高度撑满 K线图可视区域，内容区可滚动。 |
| **验收标准** | ✅ 点击任一非策略评分 Tab，浮层在 200ms 内平滑展开覆盖 K线图<br>✅ 浮层展开时不影响 K线图自身渲染（K线图不被缩放/重排）<br>✅ 点击同一 Tab、关闭按钮、浮层外部三种方式均可收起<br>✅ 点击"策略评分"Tab 确认回到 K线视图<br>✅ 浮层内容懒加载：首次点击 Tab 才请求对应 API 数据<br>✅ 切换股票时浮层自动收起<br>✅ 移动端（<768px）浮层全屏覆盖 |

#### P0-2: API 调用追踪中间件

| 属性 | 说明 |
|------|------|
| **需求描述** | 在 FastAPI 后端新增全局中间件，自动拦截所有 `/api/` 前缀的 HTTP 请求，记录调用元数据：端点路径、HTTP方法、状态码、响应时间(ms)、调用时间戳、请求参数摘要。无需在各 API 端点内手动埋点。 |
| **技术方案** | FastAPI 中间件（`@app.middleware("http")`），在请求进入时记录起始时间，请求完成后计算耗时并写入 SQLite。中间件对业务代码零侵入。 |
| **记录字段** | `id`(自增主键), `endpoint`(API路径如 `/api/fund-flow`), `method`(GET/POST), `status_code`(HTTP状态码), `response_time_ms`(响应耗时), `is_success`(是否成功: 2xx为成功), `timestamp`(调用时间), `params_summary`(查询参数摘要, 截断前200字符) |
| **存储** | SQLite 持久化（`data/api_calls.db`），重启不丢失。表名 `api_call_logs`。 |
| **数据保留** | 默认保留 90 天，超出自动清理（后台定时任务，每日执行一次） |
| **性能要求** | 中间件写入采用异步非阻塞方式，不影响 API 响应延迟（写入耗时 <1ms，使用缓冲队列批量写入） |
| **验收标准** | ✅ 所有 `/api/` 前缀请求均被记录，无遗漏<br>✅ 状态码与实际 HTTP 响应一致<br>✅ 响应时间记录误差 <5ms<br>✅ 服务重启后历史数据完整保留<br>✅ 中间件不影响 API 正常响应延迟（P99 延迟增加 <2ms）<br>✅ 超过90天的记录被自动清理 |

#### P0-3: /admin 后台管理页面

| 属性 | 说明 |
|------|------|
| **需求描述** | 新增 `/admin` 路由对应的后台管理页面，可视化展示 API 调用统计数据。页面不含复杂鉴权（当前阶段内部使用），直接访问。 |
| **页面布局** | 见下方"UI设计稿建议"章节 |
| **统计卡片** | 4 张实时统计卡：<br>1) 总调用次数（全部端点合计）<br>2) 成功率（成功数/总数，百分比）<br>3) 平均响应时间（全部端点平均，ms）<br>4) 错误调用数（非2xx状态码总数） |
| **调用明细表** | 分页表格，列：端点 / 方法 / 状态码 / 响应时间 / 调用时间 / 参数摘要。支持按端点筛选、按时间范围筛选。默认按时间倒序，每页 50 条。 |
| **错误率排行** | 按端点聚合错误率（错误数/该端点总数），降序排列，展示 TOP 10。每行含端点名、总调用数、错误数、错误率、平均响应时间。 |
| **时间筛选** | 全局时间范围选择器：近1小时 / 近24小时 / 近7天 / 近30天 / 自定义区间。影响所有统计组件。 |
| **API设计** | `GET /api/admin/stats?start={ts}&end={ts}` — 统计汇总；`GET /api/admin/calls?page=1&size=50&endpoint=&start=&end=` — 明细分页查询；`GET /api/admin/error-ranking?start=&end=` — 错误率排行 |
| **验收标准** | ✅ `/admin` 页面可正常访问，加载时间 <2s<br>✅ 统计卡片数据实时反映最新调用情况（页面刷新或每30s轮询）<br>✅ 明细表支持按端点和时间筛选，分页正常<br>✅ 错误率排行正确聚合计算<br>✅ 时间筛选器联动影响所有组件<br>✅ 无数据时显示友好的空状态提示 |

## 待确认问题

| # | 问题 | 影响范围 | 建议 |
|---|------|----------|------|
| Q1 | Tab 浮层是否需要记住用户上次查看的 Tab（下次打开同一股票时自动展开）？还是每次都从策略评分默认视图开始？ | 交互体验 | 建议每次都从策略评分默认视图开始，保持一致性，避免认知负担 |
| Q2 | API 调用追踪中间件是否需要排除健康检查端点（如 `/api/health`）和静态资源请求？ | 数据准确性 | 建议排除 `/api/health` 等心跳端点，避免噪音数据稀释统计 |
| Q3 | /admin 页面当前无鉴权，是否需要在同一局域网内限制访问（IP白名单）？ | 安全性 | P0 阶段不做鉴权，P2 补充简易密码保护 |
| Q4 | SQLite 写入采用同步还是异步？同步可能在高并发时造成瓶颈，异步需要缓冲队列 | 性能架构 | 建议异步缓冲队列批量写入（每100条或每1秒flush一次） |
| Q5 | 统计卡片是否需要实时刷新（WebSocket推送）还是手动/定时轮询？ | 实时性 vs 复杂度 | 建议P0用30秒轮询，P2再考虑WebSocket |
| Q6 | 浮层在 K线图区域的位置 — 是完全覆盖K线图，还是覆盖K线图+Tab栏之间的区域？ | 布局精确性 | 建议仅覆盖K线图渲染区域，Tab栏和策略评分内容区保持可见 |
| Q7 | API 参数摘要存储是否涉及敏感信息（如用户token）需要脱敏？ | 数据安全 | 建议中间件对 `token`/`password` 等敏感参数脱敏后再存储 |
